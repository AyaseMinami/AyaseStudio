## 源码已证实：1.9.13 常规备份

**后续方案更新（2026-09-30）**：以单入口、单份普通备份 ZIP 的用户体验为目标，分别适配已验证的旧版与新版格式；格式 5 手机 JSON 保留为兼容入口和开发对照，不作为长期要求用户同时导出两份文件的方案。用户已在本机提供手机导出与包含文件的普通备份。普通备份元数据已确认格式 6、应用版本 1.9.13、Windows x64，且 `Data/` 非空；其中还存在具有有效 SQLite 文件头的 `Data/cherrystudio.sqlite`。尚未读取该 SQLite 的 schema/聊天数据，不能凭文件存在推定其为权威聊天库，也不能将其视为格式 7。下一步优先验证候选 SQLite 与手机 JSON 中共同来源记录的语义一致性；只有候选源不可用时再深入 Chromium 原始库解析。此更新是后续实施的最新方向，文中早期手机 JSON 首批方案仅保留为调查过程记录。

## 版本边界与可行方案（推论）

官方 `v1.9.3` 源码也使用直接备份 `metadata.version: 6`、Dexie schema 10，但其 Redux Persist 版本是 206；这只支持“同属格式 6”的有限结论，不能承诺任意 1.9.x 字段完全一致。[1.9.3 元数据](https://github.com/CherryHQ/cherry-studio/blob/e72b77a09b06956383e203718b1af77e345d4725/src/main/services/BackupManager.ts#L137-L153)、[1.9.3 数据库](https://github.com/CherryHQ/cherry-studio/blob/e72b77a09b06956383e203718b1af77e345d4725/src/renderer/src/databases/index.ts#L127-L137)、[1.9.3 Persist 版本](https://github.com/CherryHQ/cherry-studio/blob/e72b77a09b06956383e203718b1af77e345d4725/src/renderer/src/store/index.ts#L85-L94)。2.1.3 则使用 **备份格式 7**，主要聊天数据库位于 `Data/cherrystudio.sqlite`，另有 `cache.json`；完整和精简备份的资源集合也不同。该分界说明现在安装的 1.9.13 无需升级来做 Issue #77 的目标格式研究，且升级后新备份不能直接当作旧格式样本。[2.1.3 格式常量与资源](https://github.com/CherryHQ/cherry-studio/blob/3b397393b129558dcfadfaf4141e2a2395ac5eeb/src/main/services/LegacyBackupManager.ts#L62-L64)、[2.1.3 元数据](https://github.com/CherryHQ/cherry-studio/blob/3b397393b129558dcfadfaf4141e2a2395ac5eeb/src/main/services/LegacyBackupManager.ts#L209-L232)、[2.1.3 文件复制](https://github.com/CherryHQ/cherry-studio/blob/3b397393b129558dcfadfaf4141e2a2395ac5eeb/src/main/services/LegacyBackupManager.ts#L367-L430)。

对 Issue #77 的建议是按 `metadata.json` 与 `data.json` 分支识别备份格式、应用版本和内部资源结构；只读入助手/话题关联、消息与正文块，并明确报告非文本块、孤儿记录、缺块、并行回答及其他无法保留的数据。可把 1.9.13 界面可生成的格式 5 `data.json` ZIP 定为首个**明确标注的受支持格式**，并清楚告知普通“备份”格式 6 暂不支持；Issue 要求明确支持格式，并未要求一次覆盖所有格式。解析常规 ZIP 的 Chromium 原始 `Local Storage` / `IndexedDB` 目录需要可靠的只读读取与隔离验证；尚无样本证明这些目录在实际导出中的精确文件布局，也不能承诺跨平台和损坏库的处理。格式 7 亦需独立验证。以上是实现建议，**不是**已验证的导入能力。

## 2.x 桌面版导出对照（固定 v2.1.3）

截至 2026-09-30，CherryHQ 发布列表中最新的非草稿、非预发布 **桌面 `v2.*`** 是 [v2.1.3（2026-09-24）](https://github.com/CherryHQ/cherry-studio/releases/tag/v2.1.3)，固定提交为 [`3b397393b129558dcfadfaf4141e2a2395ac5eeb`](https://github.com/CherryHQ/cherry-studio/commit/3b397393b129558dcfadfaf4141e2a2395ac5eeb)。GitHub 的 `releases/latest` 此时指向另一个工作区子包 `@cherrystudio/remote-transport@0.1.1`，不能据此判断桌面版。以下只证实 v2.1.3，不承诺所有 2.x 小版本一致。

- **普通备份仍是 ZIP，内部结构已变。** v2.1.3 生成备份格式 `metadata.version: 7`，并把 `appVersion` 与资源布尔值写入 `metadata.json`。ZIP 中 `Data/cherrystudio.sqlite` 是主要数据库，根目录另有 `cache.json`；完整备份还含 `Data/` 的其他文件及 `IndexedDB/`、`Local Storage/`，精简备份只保留 SQLite 与 cache。源码的恢复流程拒绝缺失 `metadata.json` 的旧 v1 备份，也只接受格式版本 7。因此格式 5 JSON、格式 6 目录和格式 7 SQLite 应独立判别，不能共用同一个聊天解析器。[格式常量和资源表](https://github.com/CherryHQ/cherry-studio/blob/3b397393b129558dcfadfaf4141e2a2395ac5eeb/src/main/services/LegacyBackupManager.ts#L62-L64)、[元数据](https://github.com/CherryHQ/cherry-studio/blob/3b397393b129558dcfadfaf4141e2a2395ac5eeb/src/main/services/LegacyBackupManager.ts#L209-L232)、[复制资源](https://github.com/CherryHQ/cherry-studio/blob/3b397393b129558dcfadfaf4141e2a2395ac5eeb/src/main/services/LegacyBackupManager.ts#L367-L430)、[恢复版本检查](https://github.com/CherryHQ/cherry-studio/blob/3b397393b129558dcfadfaf4141e2a2395ac5eeb/src/main/services/LegacyBackupManager.ts#L905-L916)。`metadata.version` 仍是**备份容器版本**，不是 SQLite 迁移版本；数据库另有 `__drizzle_migrations` 记录已应用迁移。[迁移链读取](https://github.com/CherryHQ/cherry-studio/blob/3b397393b129558dcfadfaf4141e2a2395ac5eeb/src/main/data/db/restore/appliedChain.ts#L11-L31)。

- **“导出至手机 → 导出到文件”在 2.1.3 界面不可用。** 该版的备份弹窗只调用普通 `backup()`；旧 `getBackupData()` 与 `createLanTransferBackup()` 函数尚留在源码和 IPC，但没有界面调用，源码注释明确称手机传输界面尚未开放。更关键的是，残留 `getBackupData()` 虽仍写 JSON `version: 5`，内容只含 `time` 和 `localStorage`，已经**没有** 1.9.13 的逐表 `indexedDB` 聊天导出，也不含 v2 SQLite。相同的 `version: 5` 数字因此不能证明消息载荷兼容。[2.x 备份弹窗](https://github.com/CherryHQ/cherry-studio/blob/3b397393b129558dcfadfaf4141e2a2395ac5eeb/src/renderer/pages/settings/DataSettings/BackupPopup.tsx#L8-L45)、[停用说明与残留载荷](https://github.com/CherryHQ/cherry-studio/blob/3b397393b129558dcfadfaf4141e2a2395ac5eeb/src/renderer/services/BackupService.ts#L311-L321)、[残留 ZIP 包装](https://github.com/CherryHQ/cherry-studio/blob/3b397393b129558dcfadfaf4141e2a2395ac5eeb/src/main/services/LegacyBackupManager.ts#L2098-L2137)。话题菜单仍有 Markdown 等内容导出选项，但不能替代结构化备份。[导出菜单选项](https://github.com/CherryHQ/cherry-studio/blob/3b397393b129558dcfadfaf4141e2a2395ac5eeb/src/renderer/pages/settings/DataSettings/ExportMenuSettings.tsx#L38-L128)。
- **完整和精简备份都需要保护。** SQLite `user_provider.apiKeys` 可存凭据；`file_entry` 表可引用 `Data/Files/` 内部文件或外部路径。精简备份保留文件元数据而省去 `Data/Files/` 内容，完整备份也不会自动把外部路径指向的文件打包。迁移预览必须报告附件缺失，不能把两种备份的附件可用性等同。[凭据字段](https://github.com/CherryHQ/cherry-studio/blob/3b397393b129558dcfadfaf4141e2a2395ac5eeb/src/main/data/db/schemas/userProvider.ts#L59-L69)、[文件归属和路径](https://github.com/CherryHQ/cherry-studio/blob/3b397393b129558dcfadfaf4141e2a2395ac5eeb/src/main/data/db/schemas/file.ts#L8-L55)、[精简复制规则](https://github.com/CherryHQ/cherry-studio/blob/3b397393b129558dcfadfaf4141e2a2395ac5eeb/src/main/services/LegacyBackupManager.ts#L390-L427)。

**结论与支持需求**：2.1.3 的手机文件导出既无可见入口，残留 JSON 也不携带当前 SQLite 聊天；它与 1.9.13 的格式 5 不能共用解析器。若以后支持 2.1.3，需新增受限 SQLite 读取、独立版本/迁移识别和树形消息映射，并用对应版本的合成备份验证；各格式可在完成提取后复用同一规范化聊天导入流程。当前用户为导出 1.9.13 聊天**不需要升级或另做 2.x 样本**；升级后再导出只会引入另一套格式与额外验证工作。

## 仍需用户提供什么

1. **现在无需安装最新版。** 只需用现有 1.9.13 的设置 → 数据设置 → “导出至手机” → “导出到文件”生成 ZIP，保存在本机并提供文件路径；不需要上传真实备份。若用户只希望直接导入已经存在的常规备份，提供那个 ZIP 的本地路径，以先核查元数据和容器结构。
2. 后续样本检查先限于 ZIP 文件名结构、备份元数据和聊天字段结构，不输出聊天正文或配置值。若要为开发提取样本，应在本地按白名单重建助手/话题/消息/块关联并替换正文、名称、ID、URL 等，完全丢弃其他配置；不能将原始 ZIP 或其真实字段加入 Git。合成样本至少覆盖普通单轮、多轮和并行回答，可由开发侧依据格式生成，用户不需要发送付费模型请求或自己搭建测试数据目录。
3. 有助于映射决策的信息：旧记录是否大量使用多模型并行回复，以及附件/思考内容是否必须保留。Issue 已允许对不支持内容报告降级，不需要为每个常规跳过项重新请求授权；若用户要求完整保留这些内容，则进一步明确首批范围。冲突与模型选择应作为导入预览中的明确选项，不自动激活 Cherry 供应商配置或发起请求。

实际 ZIP 的具体布局、来源应用版本与迁移结果都必须由测试样本和确定性用例验证。上述初始调查只读官方源码，不把类型声明等同于某个用户备份的已验证内容；后续结构检查也不等同于完成导入验收。

## Ayase 已有基础与需要补充的工作

已核实：Ayase 的 `AssistantPreset` 可保存助手名称、排序与默认配置，`Conversation` 可保存标题、归属和会话时间，`ChatSnapshot` 保存按顺序排列的消息；已有 `thinkingSummary` 可表达可恢复的思考文本。[工作区类型](../src/chat/workspace.ts#L6-L28)、[消息与仓库类型](../src/chat/repository.ts#L20-L48)。当前源码没有 Cherry 聊天导入入口、备份解析器或批量导入命令。`save` 是单个聊天的事务写入，现有工作区事务可供扩展，但连续调用创建助手、创建对话、保存聊天不能构成整批回滚。[保存与工作区事务](../src/chat/repository.ts#L63-L88)、[创建对话](../src/chat/repository.ts#L227-L237)、[数据库](../src/storage/database.ts#L19-L36)。

主要映射限制：当前消息没有创建时间和来源模型字段，需要新增受控的来源元数据或明确报告时间/模型信息的降级；不能把 Cherry 的模型 ID 直接作为 Ayase 已配置模型引用。当前版本切换仅作用于最后一轮的用户/助手消息对，不能直接表达历史各轮的并行模型回答；默认位置补链只给每个用户消息的首个助手回复建立关系，导入器需要依据 Cherry `askId` 显式映射或拆分对话。[版本结构](../src/chat/roundVersions.ts#L4-L16)、[回复关联](../src/chat/messageOperations.ts#L6-L15)、[模型与连接归属](../src/chat/settings.ts#L4-L35)。这些是实际需要设计的地方，不是要求用户安装软件才能解决的障碍。

建议实现路径：先在独立模块做 ZIP 识别、大小/解压预算、路径与字段校验；只从导出数据中抽取允许的聊天字段，生成无写入的预览及逐项损失报告。提交时通过 repository 的单个事务写入助手、会话、消息和来源/重复导入记录；默认不覆盖现有对象，可提供跳过或另存副本。新模型引用先保持为空，需继续聊天时由用户显式选择已有模型；不导入请求回放、工具执行、凭据或供应商配置，不触发自动命名或生成请求。事务提交前完成文件读取/解压和校验。真实备份只能留在本地，Git 中的测试样本必须是重新合成的数据。这些均为待实施方案，不改变当前持久化合同。

格式识别还需注意：格式 6/7 有独立应用版本元数据；格式 5 不能只凭 JSON 的 `version: 5` 推断导出应用版本，必须另核内部结构或用户提供的来源版本。实施时补充按 ID 联结和顺序/角色/正文、缺块与未知块、重复导入、事务中途失败、恶意与超限 ZIP、凭据排除和零网络请求的确定性测试；原始格式 6 若纳入支持，先完成隔离读取的概念验证。再执行代码门禁与内置浏览器导入交互验收；若增加原生文件读取，执行相应 Rust 检查及 Tauri 启动烟雾检查。当前仅调查文档，不运行应用测试或构建。

## 本地真实备份结构检查（2026-09-30）

用户随后提供手机导出 ZIP 的本地路径，并授权解析检查。只读检查确认：根目录是 `data.json` 与空的 `Data/`，JSON 的备份格式版本为 5；助手列表、话题元数据、`topics` 消息及 `message_blocks` 可联结，所有已引用正文块均存在，正文与思考内容为字符串。没有解压到磁盘、联网、导入 Ayase 或修改源备份；未输出正文、名称、ID 或配置值，未读取供应商字段用于任何请求。真实 ZIP、聊天内容及逐条元数据不加入仓库；这里只记录影响解析设计的结构结论，不记录私人统计和文件路径。

实际样本还证实：一个消息可关联多个正文或思考块，应按 `blocks` 顺序完整处理；存在话题 `assistantId` 与其所在助手列表不一致的历史字段，导入需确定归属优先级并报告修复；有未被消息引用的块，应只迁移引用链内的块。样本存在图片、文件和引用块，但空 `Data/` 不提供附件原文件，不能将附件元数据存在等同于文件可恢复。上述检查未实施映射或持久化，也不证明新版 SQLite 备份可导入。

对归属异常的进一步核对确认：这些话题的旧 `assistantId` 均不在备份助手名单中，而其中每条消息的 `assistantId` 都与当前助手列表归属一致；没有同一话题列入多个助手或无法找到话题消息的情况。针对这类明确的过期引用，建议以助手列表和消息共同确认的归属导入，并报告旧字段修复，无需让用户重新猜测配对。若其他备份出现多个仍有效的归属互相冲突，需单独预览并处理，不能把本样本的修复规则无条件泛化。
