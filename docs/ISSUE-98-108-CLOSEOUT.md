## 性能采集方法

入口为 [chat108 夹具](../scripts/chat108/README.md) 的 `?glass-performance=1`。使用真实 AppShell、聊天导航、ChatWorkspace、MessageList、SafeMarkdown 和 App.css；只使用隔离源合成库、内存消息与本地 canvas 背景，无供应商请求。

80 条合成消息包含中文段落、表格与代码。浅／深主题分别对照全关、仅输入框、仅侧栏、两者开启；每组包含空闲、连续程序滚动、模拟流式消息更新、工作区宽度变化四个场景。每场景等待 800ms，记录 2500ms，重复三轮并交替组合顺序。切换与初次 Markdown 挂载在采样窗口之外；这份证据不覆盖开启开关瞬间的延迟。

记录 rAF 帧间隔均值／P95／最大值、超过 32ms 的间隔数、Long Tasks 数量／时长、操作次数以及实际滤镜与导航显示状态。模拟流式输出每至少 50ms 向真实消息组件追加 24 字符，不走网络、协议解码、持久化或生产任务管理。工作区宽度在 680px 与浏览器宽度之间往返，通过实际布局／ResizeObserver 重排；它不是 OS 窗口拖拽，也不等同于触发所有视口媒体查询。

GPU、耗电及 Windows WebView2 性能仍无量化结论，不以 rAF 或长任务代替这些指标。rAF 测量浏览器回调调度间隔，不直接测 GPU 呈现帧数或输入延迟。

## 浏览器性能结果

基线 `e814e08` 加本轮 fixture 采集代码，生产构建、1440×900、页面可见，内置浏览器报告 Chrome 154 / Windows x64。80 条消息共 47,027 字符；真实导航在全部采样开始时可见，四种组合的计算滤镜符合开关，Long Tasks API 可用。没有并发运行构建、回归测试或第二份基准。

以下为三轮采样的“平均帧间隔中位数 / 单轮 P95 中位数”，单位 ms。完整保留含异常样本的 [逐次数据](ISSUE-98-PERFORMANCE-SAMPLES.json)，没有筛掉最慢的轮次。

| 主题／场景 | 全关 | 仅输入框 | 仅侧栏 | 两者开启 |
| --- | --- | --- | --- | --- |
| 浅色／空闲 | 7.85 / 8.10 | 7.83 / 8.10 | 7.83 / 8.10 | 7.86 / 8.10 |
| 浅色／滚动 | 8.24 / 8.10 | 8.21 / 8.20 | 7.97 / 8.10 | 7.93 / 8.10 |
| 浅色／模拟输出 | 7.92 / 8.10 | 7.91 / 8.10 | 7.88 / 8.10 | 7.85 / 8.10 |
| 浅色／工作区宽度变化 | 29.96 / 40.00 | 29.66 / 40.10 | 29.80 / 40.00 | 29.85 / 40.00 |
| 深色／空闲 | 7.86 / 8.10 | 7.84 / 8.10 | 7.84 / 8.10 | 7.82 / 8.10 |
| 深色／滚动 | 8.07 / 8.10 | 8.27 / 8.20 | 7.95 / 8.10 | 7.97 / 8.10 |
| 深色／模拟输出 | 7.93 / 8.10 | 7.91 / 8.10 | 7.92 / 8.10 | 7.87 / 8.10 |
| 深色／工作区宽度变化 | 33.15 / 55.00 | 30.30 / 40.10 | 29.44 / 40.00 | 30.32 / 40.10 |

空闲／滚动／模拟输出的 72 个采样窗口没有 Long Tasks；深色全关模拟输出有一次 39.3ms 帧间隔，保留在数据中。模拟输出每窗口实际更新 45–46 次。空闲的 rAF 是采集器主动调度，不表示生产页面空闲时仍自行逐帧重绘，不能推导耗电。

工作区宽度变化在全部组合均有约 30ms 的平均调度间隔，明显高于其余场景。首次 24 个宽度变化窗口中，浅色仅侧栏第三轮出现 2 个长任务／110ms；深色全关累计 10 个／656ms、仅输入框 6 个／390ms、两者开启 2 个／120ms，深色仅侧栏为零。最大单次间隔为深色全关的 86.7ms。异常并不只出现在玻璃开启时，不能把“开玻璃比关闭更快”的样本解释成玻璃优化了性能。

针对宽度变化另跑浅深各 12 个采样窗口（仍每组合三轮），其余场景不重复，共计 120 个窗口。复测的“均值中位数 / P95 中位数”为：

| 定向复测 | 全关 | 仅输入框 | 仅侧栏 | 两者开启 |
| --- | --- | --- | --- | --- |
| 浅色／工作区宽度变化 | 29.47 / 47.50 | 27.96 / 40.00 | 27.18 / 40.00 | 30.89 / 56.10 |
| 深色／工作区宽度变化 | 27.70 / 39.90 | 30.91 / 56.00 | 27.80 / 40.00 | 27.14 / 40.00 |

复测长任务在浅色全关／仅输入框／两者开启分别为 10／10／13 个、仅侧栏为零；深色分别为 11／16／0 个、仅侧栏为 1 个。波动仍跨组合出现，耗时和长任务没有随玻璃开启数量稳定增加的关系。本证据未观察到滚动／模拟输出的稳定玻璃退化，但不足以排除 GPU 合成成本或把宽度变化波动归因于某个实现细节；需要单独性能分析才能确定成因。

长历史连续重排是本轮已确认的压力边界，不因为无法归因于玻璃而标为通过或消失。此项不自动触发 UI 重设计、列表虚拟化或新状态机改造；用户实际窗口缩放体验是最后验收的一部分。本轮不承诺所有设备的 60fps。

采集结束后另用真实 680×780 浏览器视口检查：80 条消息保持挂载，导航进入覆盖模式，两块玻璃计算滤镜正确，无页面横向溢出。模拟 `prefers-reduced-transparency: reduce` 时两块滤镜均为 none、输入框使用不透明主题底色，取消模拟后恢复原滤镜；该模拟已清除。没有用 CSS 工作区变宽代替这次真实视口断点检查。
