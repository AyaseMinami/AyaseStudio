# Ayase 备份与恢复

对应 [Issue #79](https://github.com/AyaseMinami/AyaseStudio/issues/79)。本地实现使用 Ayase 自有 `.ayase` 格式，与 Cherry 备份不互通。设置 → 数据管理保留原有 Cherry 导入区块，另提供 Ayase 入口；最终主观视觉验收仍待用户确认。

## 操作

1. 等待生成、保存和资源操作结束，在设置 → 数据管理进入备份与恢复。该操作重新加载工作区，以隔离聊天、自动命名、配置保存和资源整理。未发送草稿及其附件不保留，进入前请发送或复制需要的内容。
2. 导出完整备份，包含连接配置、全局网络搜索设置，以及聊天和搜索 API Key，没有类别勾选项。只有一个“加密备份”开关，默认关闭：关闭时无需密码，直接导出明文；开启时输入密码并再次确认，仅检查两次一致，不限制最短／最长长度或字符，中文、空格和空密码均可使用。整个备份加密后才进入原生保存窗口。恢复时使用完全相同的密码；密码不上传、不持久保存，忘记无法找回。关闭开关会清空两个密码输入框。
3. 恢复时选择 `.ayase` 文件。加密文件先输入密码，成功解密且校验通过后显示版本、类别、数量、连接、密钥和加密状态。预览及冲突检查不写入当前数据。
4. 明确选择策略并勾选确认，再执行导入。替换含密钥的备份另需确认覆盖连接与密钥。返回设置会刷新并加载结果。保存窗口取消时显示未保存文件。

关闭加密时，页面提示文件保存明文 API Key，能读取文件的人也能读取密钥；导出无需额外确认。空密码也只提供格式上的加密，不提供秘密密码保护。明文密钥备份可直接校验、预览和恢复，替换密钥仍需单独确认。聊天和附件也可能含有敏感内容，请保护备份文件。这里的密码保护不改变应用日常 API Key 仍以本机明文保存的现状。用户确认以实际代码行为为准，GitHub #79 已同步为独立加密开关规则。以前不含连接／密钥的备份继续可恢复。

## 类别与策略

包含：助手默认配置及头像、对话独立配置和分支创建配置（含关闭／原生／Exa MCP／Exa API 搜索选择）、可见消息及最新轮候选版本、正文／思考／搜索记录（含 Exa 服务标识、来源和有界摘录、查询、引用映射及提示）、头像库和当前用户头像原图／裁切／缩略图、背景库及当前（含停用）背景原图／显示参数、已发送附件、工作区选择、Cherry 来源标记及历史配置迁移记录、外观／聊天宽度／新助手默认头像偏好，以及连接分组、渠道、模型、独立的 Exa MCP／API 全局搜索设置和各自 API Key。

不包含：未发送草稿及附件、生成与自动命名任务、暂停请求的继续执行快照、搜索握手／Session／认证头／原始完整网页／网络日志、远端模型目录、窗口尺寸和其他原生窗口状态、派生背景缩略图、缓存、应用二进制、非受管文件、历史私有绝对来源路径、旧浏览器存储／旧头像数据库副本。历史配置迁移记录仅作为历史保存，不恢复为活动请求配置。暂停／流式消息转为可读的未完成状态；等待／执行中的搜索转为取消，其完整消息状态转为未完成；自动命名转为手动标题，不自动续发或命名。历史来源保留，恢复与冷启动不触发搜索。背景缩略图按现有规则重建。头像缩略图属于独立持有的快照，因此包含。

| 策略 | 冲突与设置 | 模型、密钥和文件 |
| --- | --- | --- |
| 合并（默认） | 保留相同 ID 的助手、对话／聊天、头像库和历史配置；同 ID 连接保留整条现有配置；追加新对象及背景库条目。保留全局偏好、当前背景、用户头像和选择。Cherry 对话来源标记合并引用。 | 新连接使用备份密钥或空密钥；已有密钥不清空。导入配置映射到可用的已恢复／保留模型，否则取消选择并提示。 |
| 另存副本 | 助手、对话、消息、供应商、连接、模型、头像库、背景库及历史配置分配新 ID，保留现有全局偏好、用户头像和选择；来源标记保留并合并引用。 | 文件分配新 UUID，不覆盖已有文件；不重放旧连接作用域的供应商响应。备份含密钥时仅写入新连接。 |
| 替换 | 替换支持的数据表、偏好、用户头像、库、当前背景及连接配置。需要明确覆盖确认。 | 备份总是含连接及密钥；覆盖连接和密钥另需明确确认。文件分配新 UUID。 |

相同 ID 是冲突依据，不根据同名、同地址或实际模型名称猜测对象等价。合并不会用备份内容更新已有连接，包括密钥。缺失的助手／对话／文件引用、损坏资源或格式不支持会拒绝；旧来源标记可以保留已删除对象的历史 ID。当前助手、对话和资源在导出时必须可读取；缺失附件／背景不会静默略过，也不会下载 URL 或读取来源路径。

全局搜索设置独立于聊天连接，两种 Exa 服务的地址、结果数量及 Key 也相互独立。合并／另存副本保留本机全部搜索配置和 Key；替换才应用文件中包含的配置。v3 替换应用 MCP 与 API 两组配置；旧 v2 只有 MCP 配置，替换时更新 MCP 并保留本机 API 配置与 Key。历史不含凭据的 v2/v3 文件替换时保留每组对应的本机 Key，不会互相复用；本机没有配置时使用空 Key。v1 或缺失搜索设置的文件，三种模式均保留本机搜索配置／Key，没有本机配置时才使用默认配置：MCP 允许匿名，API 需要另行填写 Key 才能执行。恢复预览说明这些行为；缺失字段不会自动开启会话搜索，旧 `webSearch: true` 且无新模式字段仍表示模型原生搜索。读取旧本机单配置只在内存补齐 API 默认值，不自动写回。

## 文档格式 3，信封格式 1

UTF-8 JSON 外层：`format: ayase-studio-envelope`、`version: 1`、`encrypted` 和 `payload`。明文 payload 是含 `document`（JSON 文本）和 `sha256` 的容器。新文档为 `format: ayase-studio-backup`、`version: 3`、创建时间、导出选项、显式表数据、允许的偏好、可选连接、独立 `searchSettings` 及资源清单。v3 的 `searchSettings` 为 `version: 2` 和 `exaMcp`／`exaApi` 两组配置，每组只允许 `version: 1`、HTTPS `baseUrl`、1–10 的 `numResults`，以及包含凭据时的 `apiKey`；不含凭据时两组 Key 都省略。v2 的同字段仍是原来的单 MCP 配置。配置不会混入普通偏好或消息记录。资源清单逐项包含 ID、MIME、原始大小、Base64 字节和 SHA-256；头像 Blob 以受约束标记引用清单。原生引用仅允许专用目录中的规范 UUID v4 文件名；恢复时重映射。备份不是整目录归档，也不直接复制原始 localStorage。

开启加密时外层固定 `kdf: PBKDF2-SHA256`、`iterations: 600000`、`cipher: AES-256-GCM`，含随机 16 字节盐、12 字节 IV 及 Base64 密文。密码按 UTF-8 原值使用，派生不可导出的 256 位密钥；GCM 128 位认证标签及固定附加数据 `ayase-studio-backup|1|PBKDF2-SHA256|600000|AES-256-GCM|128` 绑定格式和算法。每次导出生成新盐与 IV。SHA-256 覆盖文档和各资源原始字节；普通备份的校验用于检测损坏，不提供来源真实性保证。含密钥的明文包可以读取；未知版本、未知加密参数和不支持字段仍拒绝。加密状态只在外层 `encrypted` 字段记录，文档 `options` 仅记录连接与密钥选择；信封、KDF、AAD 和密码语义保持 v1。仍接受文档 v1/v2 的明文与加密包，但严格拒绝向 v1 塞入 v2 搜索字段，或向 v2 塞入 v3 双配置和 `exa-api` 模式／记录。只支持文档 v1/v2 的旧客户端无法读取新 v3 文件，需要更新应用。早期实现拒绝含密钥的明文包，也需要更新后的应用读取。不会执行迁移脚本、导入代码或工具。

外部搜索快照最多 10 个来源、1 条最多 2000 个 Unicode 字符的查询、每条最多 1500 个 Unicode 字符且合计最多 8000 字符的摘录、每条最多 300 字符的标题、2048 UTF-16 单元的地址，以及最多 1000 字符的提示。v2 只接受 MCP 标识，v3 同样约束 MCP／API 两种标识。旧原生搜索沿用既有边界；所有数据仍受文档总预算约束。

密码派生和认证加密通过 Web Crypto 实现，依据 [W3C Web Cryptography](https://www.w3.org/TR/WebCryptoAPI/)；迭代值参考 [OWASP PBKDF2-HMAC-SHA256 指引](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#pbkdf2)。这不代表获得任何认证。

预算：文件 128 MiB、文档 80 MiB、非资源字符串合计 8 MiB、资源原字节合计 48 MiB、最多 2000 个资源和 100000 条消息（含候选）、递归深度 32、100 万个 JSON 节点。头像单图不超过 20 MiB，背景单图不超过 20,000,000 字节；图片任一边不超过 16384 像素且合计不超过 4000 万像素，解析图片头先检查尺寸，再完整解码。JSON/Base64 开销可能使实际可导出的内容更小。拒绝文件先于持久写入；其他未来版本仍需显式兼容设计。

## 一致性与失败恢复

数据管理在重新加载后的独占前端根运行，不挂载聊天、头像和外观控制器。启动先等待原生附件和背景共享文件锁，再处理恢复日志；普通 UI 和自动清理在恢复成功后才挂载。应用已有单实例／数据目录进程锁。原生文件只读取受管目录，拒绝既有 symlink／Windows junction／reparse point，不承诺抵抗同机恶意进程在检查后主动置换路径。

恢复先验证输入并形成计划；检查所有新 UUID 路径不存在后，将之前的八张表、受支持偏好（含独立网络搜索配置／Key）和全部预留文件引用存入 IndexedDB `backupJournal`。随后创建新文件并同步落盘，原文件保持；一个 Dexie 事务提交新表和日志 `applying` 状态；再写 localStorage。最终删除日志才是完整提交点。提交点之前任意失败或重启均回滚：先恢复数据库和偏好，再删除日志所有的新文件及其派生缩略图，最后删除日志。旧恢复日志没有捕获搜索配置时保留本机该类别；冷启动修复不访问网络。回滚失败保留日志；启动阻止其他 UI／文件清理，并提供重试。成功后旧附件／背景由原有引用整理处理，旧文件清理失败不会回滚成功数据。

这不是单个 Dexie 事务跨介质提交。断电导致底层 IndexedDB／localStorage／文件系统本身损坏不在软件回滚保证之内；不能用开发单元测试替代实际设备故障验证。

## 验收状态

确定性格式、加密、排除字段、图像预算、冲突、回滚、恢复和界面测试使用合成数据，不读取真实用户备份／凭据、不发供应商请求。完整验证和独立审查结论见 [开发指南](DEVELOPMENT.md#ayase-backup-verification-79)。原生选择／保存、真实用户备份逐类恢复、实际桌面中断／重启和最终主观视觉仍需人工验收；编译、浏览器或启动成功不能代替这些交互。
